# Coine HQ — طرح جامع نهایی (Master Plan v1)

> **تاریخ:** ۲۰۲۶-۱۰-۱۶
> **منابع ادغام‌شده:**
> - `COINE_HQ_CONSULTATION_v1.md` (Claude)
> - `CHATGPT_REVIEW_v1.md` (ChatGPT)
>
> **وضعیت:** پیش‌نویس برای تصویب مالک. **هنوز هیچ چیزی اجرا نشده.** هیچ سرور، شبکه یا ریپوی دیگری تغییر نکرده است.
>
> **قاعده‌ی خواندن:** هر جا عدد آمده و کنارش «برآورد» نوشته شده، فرض طراحی است و واقعیت تأییدشده نیست.

## ۰. خلاصه‌ی مدیریتی

1. **Coine HQ یک «سیستم‌عامل شرکت» است:** یک Control Plane مرکزی (کارتابل، پیام‌رسان، جلسات، گزارش، Audit) به‌علاوه‌ی ایجنت‌هایی که کوتاه‌عمر اجرا میشوند، و یک **دروازه‌ی سیاست‌گذار** (Tool Gateway) که تنها راه رسیدن ایجنت‌ها به سرورهاست.
2. **چشم‌انداز جاه‌طلبانه، اجرای دروازه‌دار:** دفتر مجازی، جلسه‌ی صوتی زنده و شبیه‌سازی تصمیم همه در نقشه هستند، ولی هر کدام فقط بعد از عبور از معیار مشخصش ساخته میشود.
3. **سه اصل غیرقابل‌حذف** (هر دو مشاور موافق):
   - مجوز و سیاست بیرون از LLM اجرا میشود.
   - قبل از هر افزایش استقلال، شاهد و ارزیابی لازم است.
   - قبل از بزرگ‌تر کردن مقیاس، اقتصاد واحد و Safety Gate لازم است.
4. **استقلال یک عدد کلی نیست،** بلکه برای هر **ایجنت × اکشن × محصول × ریسک** جداگانه تعیین میشود. کلاس‌های اکشن A0 تا A4 تعریف شده‌اند و **معامله، برداشت و انتقال پول برای AI در نسخه‌ی ۱ ممنوع است.**
5. **منشی وجود ندارد.** ارتباط مستقیم با هر ایجنت است. تولید گزارش یک تابع سیستمی است و نقش واسطه‌ی مکالمه ندارد.
6. **شروع کوچک:** کاتالوگ حدود ۵۸ نقش دارد، ولی **روز افتتاح ۱۰ نقش فعال** میشوند و **۲ تا ۵ اجرای همزمان** داریم.
7. **اولین خروجی ماه ۱ یک «خط کامل» است:** هشدار واقعی ← شاهد ← پیشنهاد ← کارتابل ← تصمیم مدیرعامل ← ثبت. بعد همین الگو برای همه‌ی دپارتمان‌ها تکرار میشود.
8. **هزینه‌ی AI بعد از اصلاح قیمت‌ها تقریباً نصف برآورد ChatGPT است** (§۱۲). برآورد کل پایلوت: **۱۸۰ تا ۶۰۰ دلار در ماه**.
9. **توسعه با Claude Code انجام میشود،** همان روشی که هر سه ریپوی فعلی با آن ساخته شده‌اند. پس گلوگاه اصلی سرعت کدنویسی نیست؛ **تصمیم‌ها و دسترسی‌هایی است که فقط مالک میتواند بدهد.**
10. **۱۰ تصمیم از مالک لازم است** (§۱۵). برای هر کدام یک پیش‌فرض پیشنهادی گذاشته‌ام؛ اگر همه را قبول داری، کافی است بنویسی «پیش‌فرض‌ها قبول».

## ۲. چشم‌انداز و اصول

**چشم‌انداز:** مالک مدیرعامل یک هلدینگ است که کارمندانش ایجنت‌اند. او هدف میدهد، تصمیم میگیرد و گزارش میگیرد. شرکت هر ماه با سه کار بهتر میشود: دانش انباشته (Playbook)، اعتماد اثبات‌شده (Grant) و دارایی ماندگار (محتوا، داده، مخاطب). رشد تصاعدی **تضمین نمیشود؛ اندازه‌گیری میشود.**

**ده اصل:**
1. **Control Plane واحد، Execution Plane محدود.**
2. **LLM بی‌حالت، پلتفرم باحالت:** «ایجنت» یک پروسه‌ی همیشه‌بیدار نیست. هر کار یک اجرای کوتاه‌عمر (Run) است و حالت در دیتابیس نگه داشته میشود.
3. **هیچ ارتباط شبکه‌ای مستقیم از Workerهای LLM وجود ندارد.** فقط Gateway ارتباط میگیرد.
4. **اول خواندن، بعد نوشتن.**
5. **منبع حقیقت مشخص:** حافظه‌ی ایجنت و پیام‌ها منبع رسمی KPI نیستند.
6. **در صورت خطا، سیستم بسته میشود (fail-closed)** و آخرین وضعیت را با برچسب «stale» نشان میدهد.
7. **هیچ عددی بدون منبع پذیرفته نمیشود.** هر عدد `source`، `as_of` و `unit` دارد.
8. **همه‌چیز Audit میشود** و قابل بازپخش است.
9. **هر اکشن نوشتنی idempotent است** و قبل از اجرا Dry-run دارد.
10. **ریپوها و سرورهای دیگر فقط خواندنی‌اند.** هر تغییر در آن‌ها فقط با یک Change Request جداگانه و اجازه‌ی صریح مالک انجام میشود (§۴.۶).

### ۳.۳ سه حالت اتصال به محصولات
- **حالت A (بدون هیچ تغییری روی سرور):** فقط API‌هایی که همین الان وجود دارند (Prometheus query، Grafana read API، Alertmanager API) و فقط با اجازه‌ی مالک. GitHub فقط برای خواندن ساختار کد.
- **حالت B (تغییر حداقلی):** برای **هر سرور جداگانه** یک Change Request: service account محدود، endpoint فقط‌خواندنی، allowlist فایروال، credential با TTL، و روش بازگشت.
- **حالت C (اجرای عملیات):** فقط در فازهای بعد، از طریق Action Adapter تأییدشده. هر اکشن (`restart_service`، `publish`، `send_campaign` و غیره) سیاست مستقل خودش را دارد. **`deploy` همیشه فقط از طریق PR انجام میشود.**

**شواهد فعلی از ریپوها:** CoinePro-FX روی **Hetzner Cloud** است (ریپو از Hetzner Cloud API و سرورهای سری `cx` استفاده میکند). هر سه ماشین روی یک شبکه‌ی خصوصی هستند (طبق `docs/web/SERVER.md` در CoinePro-App). نوع سرور TradeYar و Pro-Chart هنوز باید تأیید شود (سؤال ۲ در §۱۵).

### ۳.۴ مدل داده

  1. context کاری کوتاه‌عمر
  2. مکالمه
  3. Playbookهای تأییدشده
  4. دانش سازمانی با منبع و TTL

  - صوت خام: ۷ روز
  - transcript: ۳۰ تا ۹۰ روز
  - Audit امنیتی: ۳۶۵ روز
  - (تصمیم نهایی با مالک)

### ۳.۵ ظرفیت و SLO
- **سرور پایلوت:** یک ماشین ۸ vCPU / ۱۶GB (کلاس CPX42)، روی همان شبکه‌ی خصوصی، با backup خارج از سرور و مانیتورینگ بیرونی. ظرفیت هدف: ۲ تا ۵ اجرای همزمان (**برآورد؛ باید با تست بار تأیید شود**).
- **SLO بعد از پایدار شدن:**
  - ۹۹.۵٪ دسترس‌پذیری HQ
  - **صفر** اکشن بدون Grant معتبر
  - ۱۰۰٪ اکشن‌های نوشتنی دارای Audit و Idempotency Key
- **بازیابی در پایلوت:** RPO ≤ ۲۴ ساعت، RTO ≤ ۸ ساعت. تست بازیابی ماهانه. (**Backup تا وقتی بازیابی‌اش تست نشده، backup نیست.**)
- **محافظ مقصد:** آستانه‌های p95 latency، CPU، حافظه و نرخ خطا برای هر سرور تعیین میشوند. اگر telemetry معتبر نباشد، نوشتن بسته و خواندن کند میشود.

## ۴. امنیت، سیاست و اختیار

### ۴.۱ کلاس‌های اکشن
| کلاس | مثال | سیاست |
|---|---|---|
| **A0: مشاهده** | خواندن متریک، پیش‌نویس گزارش | خودکار، با سقف و scope |
| **A1: پیشنهاد** | پیش‌نویس PR، محتوا، برنامه‌ی کمپین | خودکار؛ خروجی فقط پیش‌نویس است |
| **A2: کم‌ریسک و برگشت‌پذیر** | ویرایش سند داخلی HQ، زمان‌بندی غیرحساس | L2 به بالا، با سقف |
| **A3: بیرونی / production** | انتشار پست، پیام به مشتری، restart، deploy، تغییر قیمت | **همیشه تأیید صریح موردی** |
| **A4: برگشت‌ناپذیر / مالی** | سفارش ترید، برداشت، انتقال پول، حذف backup، تغییر IAM اصلی | **برای AI در v1 ممنوع است.** باز کردنش یک پروژه‌ی مستقل با بررسی حقوقی و امنیتی است. |

### ۴.۲ نردبان استقلال (برای هر اکشن)
| سطح | اختیار |
|---|---|
| L0 | فقط مشاهده |
| L1 | پیشنهاد |
| L2 | انجام، با تأیید مالک |
| L3 | انجام و گزارش بعدی |
| L4 | کاملاً مستقل، در محدوده‌ی Escrow |

- L3 و L4 فقط برای کلاس‌های A0 تا A2 در دسترس است.
- مثال: ایجنت SEO میتواند برای «گزارش» روی L4 باشد و برای «انتشار» روی L1.

### ۴.۳ IAM و تأیید
- **مالک تنها owner نهایی است.** هیچ ایجنتی، حتی یک مدیر، نمیتواند به زیردستش اختیاری بیشتر از اختیار خودش بدهد.
- **Approval Token** به hash همان اکشن مشخص گره میخورد، یک‌بارمصرف است و TTL دارد. اگر Diff عوض شود، توکن باطل میشود.
- **وقتی شرکت تک‌نفره است** (یعنی درخواست‌دهنده و تأییدکننده یک نفرند)، تأیید با step-up MFA، یک مکث کوتاه (cooling-off) و نمایش Diff دقیق انجام میشود.
- **Kill Switch دولایه:** Scheduler متوقف میشود و Gateway همه‌ی grantها را revoke میکند. Runهای در حال اجرا امن لغو میشوند و رسید نهایی میدهند. **کاری که قبلاً اجرا شده برگردانده نمیشود.**
- **Break-glass دستی** با logging کامل.

### ۴.۴ داده و DLP
- **طبقه‌بندی داده:** عمومی، داخلی، محرمانه، PII، مالی، secret.
- **هیچ secret و هیچ PII خامی به LLM بیرونی ارسال نمیشود.** redaction قبل از ارسال، و یک egress policy روی Gateway.
- **ورودی‌های بیرونی** (وب، پیام کاربران، لاگ‌ها) **و خروجی LLM** تا وقتی Validator نپذیرفته، داده‌ی غیرقابل‌اعتمادند.

### ۴.۵ ده ریسک اصلی و کنترل هرکدام
| # | ریسک | کنترل |
|---|---|---|
| 1 | Prompt injection | ورودی‌ها untrusted؛ allowlist ابزار؛ اعتبارسنجی خروجی |
| 2 | دسترسی فراتر از scope | ABAC + grant کوتاه‌عمر |
| 3 | نشت secret یا PII | redaction، DLP، پاک‌سازی لاگ |
| 4 | اجرای تکراری | idempotency، outbox pattern |
| 5 | زیان مالی یا معاملاتی | A4 ممنوع؛ فقط مشاوره |
| 6 | تغییر production بدون تأیید | فقط PR، branch protection، CI |
| 7 | فشار روی سرورهای فعلی | query budget، circuit breaker، health gate |
| 8 | نشت داده بین شرکت‌ها | tenant scope در همه‌ی لایه‌ها، و تست cross-tenant |
| 9 | خستگی از تأیید (تأیید کورکورانه) | تجمیع درخواست‌ها، سقف تصمیم روزانه (§۸.۲)، سنجش Decision Load |
| 10 | تغییر رفتار یا قیمت مدل | ModelAdapter، eval قبل از تعویض مدل، version pinning |

ریسک‌های تکمیلی که هم پوشش داده میشوند: **Privilege Drift** (بازبینی ماهانه‌ی دسترسی‌ها)، **Token/Loop Storm** (سقف تعداد قدم و عمق، و بودجه‌ی سخت)، **False Causality** (holdout)، **Correlated Failure** (داور مستقل)، **SPOF** (backup مستقل و تمرین بازیابی).

### ۴.۶ Change Request برای ریپوها و سرورهای دیگر
هر تغییر بیرون از `CoinePro-Hub` یک CR جداگانه دارد که این‌ها را مشخص میکند: ریپو یا سرور، فایل یا سرویس، دلیل، Diff، ریسک، زمان اجرا، روش rollback، و **تأیید صریح مالک برای همان CR**. هیچ تأیید قبلی جای آن را نمیگیرد.

## ۶. موتور کار

- **کار (Work Order) سه جزء مستقل دارد:**
  - `Goal`: چه نتیجه‌ای
  - `Runbook`: با چه روشی
  - `Capability Grant/Escrow`: با چه اجازه‌ای
- **وضعیت‌ها:** `DRAFT → APPROVED → SCHEDULED → RUNNING → VERIFYING → DONE`. وضعیت‌های فرعی: `WAITING_APPROVAL`، `BLOCKED`، `FAILED`، `CANCELLED`، `COMPENSATED`.
- **چهار نوع کار:**
  - یک‌باره
  - **دائمی** (یک بار تأیید، بعد تکرار بدون اجازه‌ی مجدد، داخل Escrow)
  - رویدادمحور
  - پروژه‌ی چندایجنتی
- **ایمنی تکرار:** idempotency key، de-duplication، timeout، سقف تلاش مجدد و اکشن جبرانی.
- **OKR:** مالک هدف ماهانه میدهد. مدیر برنامه‌ای با خط پایه، هزینه، ریسک و روش سنجش ارائه میکند. مالک یک بار سقف را تصویب میکند و Runها شروع میشوند.
- **Playbook:** فقط بعد از Verify و Eval وارد کتابخانه میشود، و در Runهای در حال اجرا نسخه‌اش ثابت (pinned) میماند.

## ۹. سیستم جلسات

### ۹.۱ هر جلسه یک Workflow است
`Trigger → Agenda Builder → Evidence Freeze → Role Briefs → Independent Challenge (Red Team) → Decision Options → Policy Gate → CEO Approval (if needed) → Tasks → Outcome Check (7/30 days)`

- **Evidence Freeze:** همه‌ی شرکت‌کننده‌ها از یک snapshot با `as_of` یکسان استفاده میکنند.

- **Red Team** حداقل یک توضیح جایگزین و یک سناریوی شکست ارائه میدهد، ولی مجبور به مخالفت ساختگی نیست.

## ۱۰. ویس

- **مسیر:** `Audio → VAD → STT(fa-IR) → Editable Transcript → Agent → Verified Text → TTS(fa-IR)`.
- **Push-to-talk:** در نسخه‌ی اول میکروفون همیشه‌روشن نداریم. متن پیاده‌شده قبل از ارسال قابل ویرایش است.
- **هیچ فرمان صوتی مستقیم به `deploy`، `trade`، `withdraw`، `delete` یا `price change` وصل نمیشود.** همیشه Preview و تأیید در UI لازم است.
- **کاندیداها:**
  - STT: Azure Speech (fa-IR)، Google Cloud STT (fa-IR)، خانواده‌ی Whisper
  - TTS: Azure Neural TTS (`fa-IR-FaridNeural` و `fa-IR-DilaraNeural`) و سایر ارائه‌دهنده‌ها
  - (طبق بررسی ChatGPT؛ در زمان تست دوباره تأیید شود)
- **پروتکل انتخاب:**
  - **نمونه‌ها:** ۱۰۰ فایل کوتاه با لهجه‌های مختلف، اصطلاحات کریپتو و فارکس، عدد و درصد، و جمله‌های مخلوط فارسی و انگلیسی.
  - **STT:** نرخ خطای WER و CER، و به‌خصوص **خطای عدد و قیمت**.
  - **TTS:** امتیاز طبیعی بودن صدا و p95 latency.
  - **هدف:** ۹۵٪ فرمان‌های روزمره بعد از بازبینی متن درست فهمیده شوند، و p95 زمان تا شروع پاسخ صوتی کمتر از ۵ ثانیه باشد.
- **تماس زنده و جلسه‌ی صوتی زنده:** P2، با WebRTC و STT/TTS استریم.

## ۱۲. بیزینس‌پلن و مدل هزینه

### ۱۲.۱ قیمت مدل‌ها (اصلاح‌شده)
منبع: داده‌ی رسمی Anthropic (cache مورخ ۲۰۲۶-۱۰-۰۶). قیمت‌ها به دلار و برای هر یک میلیون توکن است.

| مدل | ورودی | خروجی | توضیح |
|---|---:|---:|---|
| `claude-haiku-5-5` | $0.10 | $0.50 | برای prompt تا ۱۰۰K توکن؛ بالاتر از آن $0.50 / $2.50 |
| `claude-sonnet-5-5` | $2.00 | $10.00 | خواندن از cache: $0.20 |
| `claude-opus-5-5` | $4.00 | $20.00 | خواندن از cache: $0.20 |
| `claude-fable-5-1` | $10.00 | $50.00 | فقط موارد خاص |

- **Batch API:** ۵۰٪ ارزان‌تر برای کارهای غیرفوری مثل گزارش شبانه و ممیزی SEO.
- **Prompt caching:** خواندن از cache خیلی ارزان‌تر است، به شرطی که system prompt و ابزارها ثابت بمانند.
- **⚠️ توکن‌های فکر کردن هزینه‌ی خروجی حساب میشوند.** روی Opus 5.5 فکر کردن را نمیشود خاموش کرد، پس هزینه با `effort` کنترل میشود (`low` برای روتین).

### ۱۲.۲ تکرار مثال ChatGPT با قیمت‌های درست
فرض ChatGPT: ۱۸٬۰۰۰ job در ماه، و یک فراخوانی برای هر job.

| سطح | سهم | job در ماه | ورودی / خروجی برای هر job | هزینه |
|---|---:|---:|---|---:|
| S / Haiku 5.5 | ۸۰٪ | ۱۴٬۴۰۰ | ۲٬۰۰۰ / ۴۵۰ | **$6.12** |
| M / Sonnet 5.5 | ۱۸٪ | ۳٬۲۴۰ | ۴٬۰۰۰ / ۱٬۰۰۰ | **$58.32** |
| H / Opus 5.5 | ۲٪ | ۳۶۰ | ۸٬۰۰۰ / ۲٬۰۰۰ | **$25.92** |
| **جمع** | | **۱۸٬۰۰۰** | | **$90.36** |

- ChatGPT همین مثال را **$181.08** حساب کرده بود.
- با میانگین ۲.۵ فراخوانی برای هر job، جمع حدود **$226** میشود. توکن فکر کردن، retry و context طولانی این عدد را بالاتر میبرند؛ caching و Batch پایین‌تر.
- **نتیجه‌ی مهم:** Haiku 5.5 آن‌قدر ارزان است که پایش و triage تقریباً هزینه‌ای ندارد. **هزینه‌ی واقعی را سطح M و H تعیین میکنند.** پس سیاست «H فقط در جلسه» مهم‌ترین اهرم صرفه‌جویی است.

### ۱۲.۳ سه سناریوی ماهانه (برآورد، بدون هزینه‌ی توسعه)
| قلم | پایلوت (۸ تا ۱۲ نقش، ≤۳ هزار job) | عملیاتی (۳۰ تا ۵۰ نقش، ۱۰ تا ۲۰ هزار job) | گسترش (۷۰ تا ۱۲۰ نقش، ۴۰ تا ۸۰ هزار job) |
|---|---:|---:|---:|
| سرور، دیتابیس، backup، storage | $110–220 | $180–450 | $450–1,200 |
| LLM (با judge و retry) | $30–150 | $150–700 | $500–2,500 |
| STT/TTS | $5–40 | $20–150 | $100–500 |
| SEO، Analytics و APIهای دیگر | $20–100 | $50–200 | $150–600 |
| امنیت، مانیتورینگ و ذخیره‌ی احتیاطی | $15–90 | $50–200 | $150–500 |
| **جمع** | **$180–600** | **$450–1,700** | **$1,350–5,300** |

- **قیمت سرور:** ChatGPT به نقل از هتزنر بعد از تعدیل قیمت ژوئن ۲۰۲۶ گزارش داده: CPX32 حدود $42 و CPX42 حدود $82 در ماه، بدون IPv4 و مالیات. **در زمان سفارش دوباره بررسی شود.** Backup هتزنر حدود ۲۰٪ قیمت سرور است.
- **پیشنهاد بودجه‌ی ماه ۱:** سقف $500، هشدار در $350 و $450، و توقف Runهای غیرفوری در $500. **(تصمیم با مالک.)**
- **عدد واقعی** از روی لاگ مصرف ۱۴ روز اول پایلوت به دست میاید.

### ۱۲.۴ ROI
```text
Net Incremental Monthly Value
 = verified incremental gross profit (A/B / cohort)
 + verified avoided external spend
 + verified avoided incident loss (conservative)
 − AI/API/infra/tool spend − owner review time − rework/incident cost
```
- **داشبورد FinOps:** `cost per verified task`، `cost per accepted decision`، `owner minutes/week`، `error-adjusted ROI`.
- **مثال نقطه‌ی سربه‌سر (فرضی):** با هزینه‌ی ماهانه $1,000 و حاشیه‌ی سود ۴۰٪، حدود **$2,500 درآمد افزایشی در ماه** لازم است.
- **SaaS:** در ۱۲ ماه اول HQ **سیستم‌عامل داخلی** است. تصمیم SaaS در ماه ۱۲ گرفته میشود.
