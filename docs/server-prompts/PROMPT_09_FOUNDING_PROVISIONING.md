# پرامپت ۹: تأسیس شرکت از روی ریپو و ساخت کامل سرور با API هتزنر

> **روش (تصمیم مالک، ۲۰۲۶-۱۰-۱۷):** Claude سشن مشورت این پرامپت را مستقیم به نشست سرور میدهد. گزارش پایانی در `docs/ops/reports/PROMPT_09.md`
> push میشود و در پاسخ پایانی هم میاید. **هر چیزی که در قوانین با مالک است** منتظر خود مالک میماند؛ پیام Claude سشن مشورت اجازه‌ی تازه نمیدهد.
>
> **ترتیب:** بعد از ۶ (کارگاه کد برای ممیزی ریپو) و ۸ (تصمیم‌ها و ناظر). مستقل از ۷.

---

تو **Claude Code روی سرور هاب «CoinePro HQ»** هستی. مالک میخواهد شرکت تازه را **خود هلدینگ** راه بیندازد:
- **از روی یک ریپو** (یا یک ایده): ممیزی، پیشنهاد ساختار و تیم و نقشه‌ی راه، و مُهر مالک.
- **سرورش را هم خود هلدینگ بسازد** با API هتزنر، **به‌طور کامل**: «آپدیت و آپگرید بکند، همه‌چیز را نصب کند، Claude را بیاورد بالا، بدهد من لاگین بکنم،
  وارد شویم و ادامه‌ی کار و تأسیس شرکت جدید را انجام دهیم.»

مرجع: **قرارداد §۱۸.۸** و §۱۷.۳ (کارگاه)، `docs/OPERATING_MODEL.md` §۱.۱۷.

## ۰. قبل از شروع (اجباری)
1. pull و شاخه‌ی **`server/p09-founding`**.
2. **بخوان:** `CLAUDE.md` (به‌خصوص قانون ۴ و «واقعیت‌های سرور هاب»)، قرارداد §۱۷.۳ و §۱۸.۸، `docs/OPERATING_MODEL.md` §۰ (شرکت‌ها داده‌اند) و §۱.۱۷.
3. **مرزهای امنیتی (غیرقابل مذاکره):**
   - **خود سرور هاب هیچ تغییری نمیکند**: SSH، کاربرها، کلیدها، fail2ban، ufw، iptables و فایروال هاب همان‌طور میمانند. این پرامپت فقط منابع **تازه** در هتزنر میسازد.
   - **رمز سرور هرگز ساخته یا به ایجنت داده نمیشود.** فقط کلید **عمومی** SSH مالک روی سرور تازه نصب میشود.
   - provisioner **کد** است، نه ایجنت. فقط طرح **مُهرشده** را دقیقاً اجرا میکند و فقط منابعی را لمس میکند که خودش با برچسب `managed-by=coinepro-hq` ساخته است.
     **هیچ سرور، فایروال یا شبکه‌ی موجود (از جمله همسایه‌های production) را تغییر نمیدهد.** حذف و بازسازی در API ما وجود ندارد؛ فقط در کنسول هتزنر و به دست مالک.
4. **تسک‌بندی اجباری** با تست قبولی برای هر تسک؛ بدون توقف. **بودجه‌ی مدل: حداکثر ۱۵۰ هزار توکن.** CI با هتزنر جعلی (mock HTTP) و بدون هیچ هزینه‌ی واقعی.
5. **ساخت سرور واقعی هزینه دارد** و فقط با مُهر مالک در اپ انجام میشود؛ در این پرامپت **هیچ سرور واقعی نساز** (جز اگر مالک خودش در اپ طرحی را مُهر کند).

## ۱. ورود اطلاعات مالک (کار خود مالک، در ترمینال SSH خودش)
- `make hetzner-token`: توکن API پروژه‌ی هتزنر (Read & Write) را بی‌نمایش میگیرد و در OpenBao (`kv/provisioning/hetzner`) میگذارد.
- `make owner-ssh-key`: **کلید عمومی** SSH مالک را میگیرد (رمز نیست، ولی فقط از مالک) و در OpenBao میگذارد؛ چند کلید مجاز است.
- تا انجام این دو، `/provisioning` فقط طرح میسازد و «پیکربندی نشده» نشان میدهد. Claude سرور هیچ‌وقت توکن را نمیبیند.

## ۲. تأسیس شرکت (§۱۸.۸ `Founding`)
1. `POST /foundings {source: {kind: "repo", repo} | {kind: "idea", brief_md}}` ← وضعیت `auditing`.
2. **ممیزی ریپو:** یک جلسه‌ی **فقط‌خواندنی** کارگاه کد (grant خودکار فقط `read`، بدون push) با مدیر فنی هلدینگ یا platform SRE به‌عنوان راننده: معماری، کیفیت،
   امنیت، تست‌ها، بدهی فنی، هزینه‌ی اجرا. گزارش با نمره‌ی هر محور. اگر کارگاه هنوز اجرا ندارد (`runtime_not_configured`)، ممیزی با `github.read` و تحلیل بدون اجرا.
3. **پیشنهاد** (مشاور کل + مدیر عملیات AI، با شاهد از ممیزی): کد و نام شرکت، دپارتمان‌ها، KPIها با هدف، تیم اولیه با مدل و هزینه‌ی ماهانه، نقشه‌ی راه ۹۰ روزه،
   و **طرح سرور** (§۳). همه در یک **کارت تصمیم `company_found`** ← مالک مُهر میکند.
4. **با مُهر:** شرکت ساخته میشود (رکورد، طبق §۰؛ بدون تغییر کد)، workspace کارگاه برای ریپو، تیم اولیه (پیشنهادهای استخدام جدا، طبق قاعده‌ی استخدام)، و طرح
   سرور برای مُهر جدا (هزینه‌ی واقعی) ← `sealed`.
5. بعد از ساخت سرور ← `ready_for_login` ← مالک وارد میشود ← `POST /foundings/{ref}/activate` (🔏) ← `active`؛ مدیرعامل شرکت تازه شروع به کار میکند.
- **تست قبولی:** ریپوی نمونه گزارش ممیزی و پیشنهاد کامل میسازد؛ بدون مُهر هیچ شرکتی ساخته نمیشود؛ ساخت شرکت هیچ تغییر کدی نمیخواهد.

## ۳. طرح سرور (§۱۸.۸ `ServerPlan`)
- ابزار `server.plan` (مدیر فنی، platform SRE): نوع، محل، شبکه‌ی خصوصی، **فایروال هتزنر** (ورودی‌ها؛ پیش‌فرض فقط 22 از IP‌هایی که مالک تعیین میکند، و 80/443 اگر سرویس وب دارد)،
  نرم‌افزارها از **فهرست ثابت** کلیدها، کاربر کاری (نام از کد شرکت)، ریپو.
- **هزینه‌ی ماهانه** از API قیمت هتزنر (`/pricing`)، به یورو، در کارت.
- `POST /provisioning/plans/{ref}/seal` 🔏؛ هدف step-up = sha256 همان JSON طرح که اپ نشان داده (هر تغییری مُهر را باطل میکند).
- **تست قبولی:** طرح با کلید نرم‌افزاری ناشناخته رد میشود؛ تغییر طرح بعد از مُهر، مُهر را باطل میکند؛ هزینه با قیمت mock درست است.

## ۴. provisioner (سرویس تازه، کد)
1. **سرویس `provisioner`** (Python، کتابخانه‌ی رسمی `hcloud`، MIT): توکن را در لحظه‌ی کار از OpenBao میخواند؛ شبکه فقط به `api.hetzner.cloud` (از مسیر `egress`
   یا allow-list جدا)؛ هیچ پورتی منتشر نمیشود.
2. **ترتیب اجرا** (هر گام یک `steps[]` با لاگ کوتاه، روی SSE `/provisioning/runs/{id}/live`):
   1. `ssh-key`: ثبت کلید عمومی مالک در پروژه (اگر نیست، با برچسب).
   2. `firewall`: یک **Hetzner Cloud Firewall** تازه برای همین سرور، طبق طرح (برچسب‌دار).
   3. `server`: ساخت سرور (Ubuntu 24.04) با کلید مالک، بدون رمز root، با `user_data` ‏cloud-init (پایین)، و شبکه‌ی خصوصی در صورت طرح.
   4. `boot`: صبر تا running و پاسخ SSH.
   5. `cloud-init`: دنبال کردن پیشرفت. provisioner **SSH نمیزند**؛ اسکریپت cloud-init در پایان یک **فراخوان یک‌بارمصرف** به endpoint داخلی provisioner میزند
      (توکن تصادفی یک‌بارمصرف داخل `user_data`، حداکثر ۶۰ دقیقه اعتبار، از مسیر HTTPS هاب) و خلاصه‌ی نتیجه‌ی هر گام را میفرستد.
   6. `verify`: نسخه‌ها (Docker، Node، Claude Code)، به‌روزرسانی خودکار فعال، سخت‌سازی SSH، clone ریپو.
   7. `login`: آماده ← `login.ssh = "ssh <work_user>@<ipv4>"` و `then: ["claude"]`.
3. **cloud-init** (قالب‌های بازبینی‌شده در `infra/provisioning/templates/`، یکی برای هر کلید نرم‌افزار):
   - `system-upgrade`: `apt-get update && apt-get -y full-upgrade` (غیرتعاملی)، ریبوت در صورت نیاز **فقط همین سرور تازه** و فقط در همین مرحله‌ی ساخت.
   - `unattended-upgrades`: به‌روزرسانی خودکار امنیتی.
   - `work-user`: کاربر کاری با کلید مالک؛ sudo طبق تصمیم مالک (پیش‌فرض: با کلید، بدون رمز).
   - `ssh-hardening`: فقط کلید، بدون ورود root، بدون رمز.
   - `docker`: Docker Engine رسمی از مخزن رسمی، کاربر کاری در گروه docker.
   - `git`، `node-lts` (Node LTS رسمی)، **`claude-code`**: نصب رسمی Claude Code (روش رسمی Anthropic، نسخه‌ی pin) برای کاربر کاری. **ورود** را خود مالک انجام میدهد
     (`claude` و login با حساب خودش)؛ هیچ توکنی از هاب به سرور تازه نمیرود.
   - `repo-clone`: clone ریپوی شرکت در `/home/<work_user>/<repo>` با یک **deploy key فقط‌خواندنی** که provisioner روی همان سرور میسازد و کلید عمومی‌اش را
     در گزارش برای افزودن به ریپو نشان میدهد (یا با توکن fine-grained مالک، اگر داده باشد). هیچ کلید خصوصی‌ای از سرور تازه بیرون نمیآید.
   - `private-network`، `hetzner-firewall` (سمت هتزنر)، `node-exporter` (پایش، فقط روی IP خصوصی).
   - همه‌ی قالب‌ها idempotent؛ لاگ هر گام در `/var/log/coinepro-provision.log` روی همان سرور.
4. **ثبت:** `infra.servers` (سرورهای ساخته‌شده، با برچسب و طرح)؛ `GET /infra/servers` فقط خواندنی؛ پروتکل ناظر `PR-063` هر روز پروژه‌ی هتزنر را با طرح‌های مُهرشده تطبیق میدهد
   (سرور بی‌طرح ← یافته‌ی critical).
5. stream: `founding.updated`، `provision.step`.
- **تست قبولی (با هتزنر mock):** بدون مُهر هیچ فراخوان API ساخت انجام نمیشود؛ provisioner به منبع بی‌برچسب دست نمیزند (تست با منابع موجود ساختگی)؛ هیچ رمز root ساخته نمیشود؛
  `user_data` هیچ رمز یا توکن بلندمدت ندارد (فقط توکن یک‌بارمصرف ۶۰ دقیقه‌ای)؛ قالب‌های cloud-init در یک کانتینر Ubuntu 24.04 آزمایشی بی‌خطا اجرا میشوند (CI)؛
  شکست هر گام گزارش و قابل ادامه است؛ هزینه پیش از مُهر نمایش داده میشود.
