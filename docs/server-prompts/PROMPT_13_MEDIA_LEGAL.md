## ۲. استودیوی رسانه (§۲۲.۲)
1. **داده:** `media.series` (`SR-0001`)، `media.items` (`MI-0001`)، `media.voices`. شکل‌ها دقیقاً مثل §۲۲.۲.
2. **برنامه‌ی انتشار (Series):**
   - مدیر رسانه با `series.propose` پیشنهاد میدهد یا مالک میسازد. مُهر: `POST /media/series/{ref}/seal` 🔏 روی `digest`.
   - **ویرایش برنامه‌ی مُهرشده آن را به `proposed` برمیگرداند** و تا مُهر دوباره هیچ چیز خودکار منتشر نمیکند.
   - schedule با RRULE در منطقه‌ی زمانی مالک؛ هر اجرا یک `MediaItem` با موضوع بعدی از `topics.pool` میسازد.
3. **خط تولید** (هر گام یک work item برای نقش همان گام؛ جابه‌جایی بین گام‌ها با کد):
   - **سناریو** (`scriptwriter`) ← **کارگردانی** (`video_director`) ← **ترکیب‌بندی** (`motion_designer`) ← **صدا** (`voice_producer`) ← **render** (کد) ← **چک‌ها** (کد + `media.review`).
   - **ترکیب‌بندی به‌صورت کد:** یک سند HTML (CSS animation، SVG، Web Animations API، `anime.js` MIT) یا Lottie JSON (`lottie-web` MIT)، طبق یک schema محدود:
     - بدون شبکه، بدون اسکریپت بیرون از کتابخانه‌های مجاز (نسخه‌ی pin‌شده، از داخل image، نه CDN)
     - تنها قلم IRANYekanX؛ پالت و نشان شرکت از §۱۸.۱۴
     - عکس فقط از فایل‌های شرکت یا `substitute.call` `creative` (§۲۱.۱۳)
     - سند با sha256 ذخیره میشود؛ هر تغییر نسخه‌ی تازه است
   - **render worker** (سرویس یک‌بارمصرف تازه، profile `media`):
     - Chromium بی‌سر (Playwright) سند را **frame به frame** با زمان کنترل‌شده render میکند (نه ضبط زنده‌ی صفحه)؛ `ffmpeg` صدا، موسیقی مجاز (اگر هست) و زیرنویس فارسی سوخته را mux میکند.
     - **سندباکس:** بدون شبکه (حتی egress)، rootfs فقط‌خواندنی، کاربر غیر root، `cap_drop: ALL`، سقف CPU و زمان (پیش‌فرض ۱۰ دقیقه) و حافظه؛ سند به‌عنوان داده‌ی نامطمئن.
     - خروجی برای هر `placement`: ۱۰۸۰×۱۹۲۰ برای ریلز و استوری، ۱۰۸۰×۱۳۵۰ پست، با codec و حجم مجاز همان پلتفرم.
     - پردازش خروجی از §۱۷.۱ رد میشود.
   - **چک‌ها با کد:**
     | چک | قاعده |
     |---|---|
     | `brand` | فقط IRANYekanX؛ رنگ‌ها از پالت شرکت؛ نشان در جای خودش |
     | `red_lines` | الگوهای `red_lines` اساسنامه (§۲۰.۲) روی سناریو، متن روی تصویر و زیرنویس |
     | `risk_warning` | هر محتوای ترید هشدار ریسک دارد (هم در صدا یا زیرنویس، هم در caption) |
     | `facts` | هر عدد سناریو منبع دارد |
     | `rights` | فقط فایل خود شرکت، ساخته‌شده یا موسیقی کتابخانه‌ی مجاز |
     | `platform` | نسبت، طول، حجم و codec طبق محدودیت خود پلتفرم |
     | `qc` | رأی `media.review` مدیر رسانه |
   - **انتشار با کد، فقط از API رسمی:**
     - برنامه‌ی مُهرشده با `auto_publish` و همه‌ی چک‌ها `pass` ← در زمان برنامه منتشر میشود. وگرنه `waiting_owner` و کارت `media_publish` (A3).
     - **تلگرام:** Bot API (`sendVideo`، `sendPhoto`، `sendMediaGroup`) با ربات مدیر کانال. **استوری کانال تلگرام در Bot API نیست**: همیشه کارت با فایل برای مالک.
     - **اینستاگرام:** Instagram Graph API برای حساب business (container ← publish؛ `media_type` REELS، STORIES یا تصویر/carousel)، با `is_ai_generated: true`.
       اینستاگرام فایل را از URL عمومی میگیرد: **یک URL امضاشده برای همان یک فایل، حداکثر ۱۵ دقیقه**، از Caddy روی `hq.coinepro.com`؛ هر URL دیگری ۴۰۴.
     - سقف خود پلتفرم (اینستاگرام: ۵۰ پست API در ۲۴ ساعت برای هر حساب) ← `429 platform_limit`.
     - کلید توقف شرکت، deploy freeze، hold و حالت نگهبان انتشار را متوقف میکنند.
     - **هیچ انتشاری از مرورگر یا کوکی نیست.**
   - **حذف پست منتشرشده:** `POST /media/items/{ref}/unpublish` 🔏، از همان API در جایی که پلتفرم اجازه میدهد.
4. **بازطراحی UI** (`ui_designer`): خروجی طراحی با mockupهای HTML که همان render worker به screenshot تبدیل میکند؛ عکس‌ها از بازیکن‌های ذخیره؛ برند §۱۸.۱۴.
   تحویل به CTO؛ ساختنش کار کارگاه کد است و deployش کارت.
5. **ابزارهای ایجنت** (`agents/tools.md`): `media.item` (A1)، `media.render` (A2)، `media.voice` (A2)، `media.review` (A2، فقط مدیر رسانه)، `series.propose` (A1).
6. **پروتکل ناظر:** هر روز نمونه‌ای از پست‌های منتشرشده را با چک‌ها و خطوط قرمز دوباره میسنجد؛ پست مشکل‌دار ← یافته و توقف همان برنامه تا مالک.
- **API:** طبق جدول §۲۲.۲. stream: `media.item` روی topic `media`.
- **تست قبولی:**
  - برنامه‌ی مُهرنشده هیچ چیزی منتشر نمیکند (`409 series_not_sealed`)؛ ویرایش برنامه‌ی مُهرشده مُهر را برمیدارد.
  - یک آیتم نمونه از سناریو تا render و چک‌ها میرود (مدل جعلی) و با API ساختگی تلگرام و اینستاگرام منتشر میشود.
  - یک چک `fail` (مثلاً بدون هشدار ریسک) ← `waiting_owner` و کارت، نه انتشار.
  - سند ترکیب‌بندی با `fetch` یا `<script src=https://…>` ← رد؛ render worker به هیچ شبکه‌ای نمیرسد.
  - URL امضاشده بعد از ۱۵ دقیقه ← ۴۰۴؛ URL فایل دیگر ← ۴۰۴.
  - کلید توقف شرکت انتشار زمان‌بندی‌شده را نگه میدارد.

## ۳. مشاور حقوقی (§۲۲.۴)
1. **داده:** `legal.cases` (`LC-0001`)، با timeline؛ رشته‌ی `L` («حقوقی»، `L-0001`).
2. **ایمیل:**
   - یک صندوق هلدینگ، حساب سرویس `mail` (IMAP و SMTP، یا API رسمی همان سرویس)، ورود با `make account-secret` به دست مالک؛ egress فقط به hostهای همان سرویس.
   - `email.draft` (A1) ← کارت `email_send` با **پیام دقیق** (from، to، cc، subject، body، hash پیوست‌ها). تأیید (🔏) **دقیقاً همان را یک بار** میفرستد؛ هر تغییر کارت تازه میخواهد.
   - **جواب‌ها:** یک poller هر ۵ دقیقه جواب پیام‌های پرونده‌ها را (با `Message-ID` و `References`) میخواند، ماسک میکند، به timeline اضافه میکند و مشاور را بیدار میکند.
     **هیچ ایمیلی خودکار فرستاده نمیشود.** پیوست‌ها از §۱۷.۱ رد میشوند. ایمیل نامرتبط وارد پرونده نمیشود.
3. **فرم و پورتال** (فرم اعتراض، تیکت مرکز پشتیبانی): مشاور مقدار دقیق هر فیلد را در کارت میگذارد؛ مالک خودش میفرستد (معمولاً ورود همان حساب لازم است)؛ نتیجه در پرونده ثبت میشود.
4. **ابزارها:** `case.open`، `case.note` (A1)، `email.draft` (A1 ← کارت)، `mail.read` (A0، فقط پرونده‌های خودش).
- **API:** طبق جدول §۲۲.۴. stream: `legal.case` روی topic `legal`.
- **تست قبولی:**
  - پیش‌نویس ایمیل بدون تأیید فرستاده نمیشود؛ تأیید دقیقاً همان پیام را یک بار میفرستد (SMTP ساختگی)؛ تغییر بعد از دیدن مالک ← کارت تازه.
  - جواب ساختگی به پرونده‌ی درست میرسد و مشاور را بیدار میکند؛ ایمیل نامرتبط وارد نمیشود.
  - مشاور به پرونده‌ای که مال او نیست دسترسی ندارد؛ رمز صندوق در هیچ لاگ یا پاسخی نیست.

## ۴. صدا: متن‌باز، روی هاب، انتخاب با گوش مالک (§۲۲.۳)
1. **بدون سرویس پولی صدا.** همان موتور برای گزارش صوتی §۲۱.۴ هم به کار میرود (یک registry، `media.voices`).
2. **آزمون مقایسه (bake-off)، اندازه‌گیری‌شده:**
   - **متن‌های آزمون فارسی ثابت:** عدد و درصد، اصطلاح لاتین (Bitcoin، RSI)، کلمه‌های کریپتو، یک جمله‌ی بلند، و یک متن ۶۰ ثانیه‌ای ریلز.
   - برای هر نامزد: RTF و پیک RAM روی CPU هاب، و فایل‌های صوتی برای **شنیدن کور مالک در اپ** (`owner_score` از ۱ تا ۱۰).
3. **نامزدها** (لایسنس همان‌طور که روی کارت خودشان آمده):
   - صداهای Piper `fa_IR` (MIT؛ سریع و ساده).
   - **صدای آموزش‌دیده روی ManaTTS** (CC0، ۸۶ ساعت، یک گوینده‌ی زن) با معماری مجاز (Piper/VITS یا Matcha-TTS، MIT). آموزش GPU میخواهد؛ کرایه‌ی GPU تصمیم و هزینه‌ی مالک است (§۰.۹ بند ۳). تا آن موقع فقط برنامه و برآورد را بنویس.
   - مدل‌های چندزبانه با لایسنس Apache-2.0 یا MIT، **فقط اگر کارت خودشان فارسی را دارد**.
   - ParsVoice-XTTS (Coqui Public Model License) و Chatterbox فارسی (CC BY-NC) روی کارت‌شان غیرتجاری‌اند: اندازه‌گیری میشوند، ولی **بدون انتخاب صریح مالک فعال نمیشوند**.
4. **فعال شدن:** بهترین صدای قابل استفاده‌ی تجاری بعد از شنیدن مالک. هر `Voice` لایسنسش را دارد و `licence_commercial: false` همه‌جا نشان داده میشود.
- **تست قبولی:** registry نامزدها را با لایسنس و عدد اندازه‌گیری‌شده دارد؛ صدای غیرتجاری بدون انتخاب مالک `active` نمیشود؛ خروجی صدا از پردازش §۱۷.۱ رد میشود.
