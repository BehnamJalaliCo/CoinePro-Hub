## §۱. API
1. **`GET /work?created_by=owner`:** فیلتر `created_by` را بپذیرد. مقدار آن `owner` یا یک کد ایجنت است.
   - امروز اپ ۱۰۰ کار آخر را میخواند و فرمان‌های مالک را خودش جدا میکند، پس فرمان قدیمی‌تر از دست میرود.
2. **`GET /work/{id}`:** هر عضو `children` این فیلدها را داشته باشد:
   - `ref`، `title`، `status` و `assignee`
   - `updated_at`
   - `progress`: آخرین گزارش `/internal/v1/work/{id}/progress`، عددی بین 0 و 1، یا null
   - `deliverable_refs`

   تا دو سطح پایین (عمق ≤ ۲). امروز اپ برای هر زیرکار یک تا سه درخواست جدا میزند.
3. **`GET /work/{id}/tree-events`:** رویدادهای خود کار و همه‌ی زیرکارهایش، یک‌جا و به ترتیب زمان.
   - صفحه‌بندی همان `Page` است.
   - گام‌های اجرا فقط خلاصه باشند، مثل §۱۶.
4. **خروجی‌ها:**
   - `GET /deliverables?work=<id>` فیلتر کار را بپذیرد.
   - `Work` در کنار `deliverable_ids` فیلد `deliverable_refs` هم داشته باشد. امروز `/deliverables/{ref}` فقط ref میگیرد و `deliverable_ids` همه UUID است.
5. **stream:** هر رویداد `work.*` و `deliverable.created` در payload فیلدهای `root_id` و `root_ref` را داشته باشد. اپ با آن میفهمد تغییر یک زیرکار مال کدام فرمان مالک است.
6. **اعلان روی گوشی وقتی اپ بسته است:** این بند فقط سنجش است، چیزی نساز.
   - هاب از پرامپت ۴.۲ Web Push دارد، اما برای اندروید FCM حذف شده است.
   - بسنج آیا UnifiedPush یا ntfy (رایگان و متن‌باز، self-hosted روی همین هاب، فقط روی `127.0.0.1` و پشت Caddy) شدنی است.
   - هزینه‌ی حافظه و کار لازم را در گزارش بنویس.
   - تصمیم با مالک است.

## §۲. تست‌ها
1. فیلتر `created_by`.
2. شکل `children`، با `progress` و `deliverable_refs`.
3. `tree-events`:
   - ترتیب زمانی
   - عمق ۲
   - RLS
4. `root_id` در رویدادهای stream زیرکار.
