# پرامپت ۱۹.۲: مُهر مدیر کل روی کارت نگه‌داشته، و خواندن فایل حساس (فقط deploy)

> Claude سشن مشورت، ۲۰۲۶-۱۱-۰۱. کد را سشن مشورت نوشته و تست کرده است. **فقط deploy.**
> - **شاخه:** `server/p19-2-deploy` از سر شاخه‌ی اصلی، بعد از pull.
> - **گزارش:** `docs/ops/reports/PROMPT_19_2.md`.

## چه شد
مالک روی یک کارت «کار ویرانگر» در تریدیار مُهر زد و جواب گرفت «این کار را ناظر کل تا تصمیم مدیر کل نگه داشته است». دو اشکال بود:

1. **مُهر مدیر کل خودش آزادکننده است.** تا امروز تأیید کارتی که ناظر نگه داشته بود `423 held` میداد و مالک باید جدا hold را آزاد میکرد.
   - **اصلاح در `domain/decisions.py`:** تأیید خود مالک با همان مُهر، hold را آزاد میکند، با یادداشت «با مُهر مدیر کل روی همین کارت آزاد شد»، و کارت جلو میرود.
   - **ایجنت‌ها:** تأیید یک ایجنت (مثلاً مدیرعامل) همچنان `423` میگیرد.
2. **یک خواندن ساده کارت ویرانگر ساخته بود.** دستور این بود:
   ```
   cat /etc/passwd 2>&1; ... sudo -n ls ... | head -40
   ```
   - **علت:** `2>&1` در نقطه‌ی `&` شکسته میشد، و `sudo -n` دستور بعدش را میبلعید.
   - **اصلاح در `domain/server_classify.py`:**
     - کپی توصیفگر (`2>&1`) جداکننده نیست.
     - هر prefix فقط پرچم‌های مقدارگیر خودش را دارد.
     - `sed -i` / `perl -i` نوشتن است، نه خواندن.
   - **تست:** `tests/test_p19_2_classify.py`. جدول ۴۸ مورد قبلی هم بی‌تغییر سبز است.

## deploy
1. `git pull`، و `make check` در worktree جدا. اجازه‌ی دائمی قالب‌بندی و CVE سر جایش است.
2. `make backup`. این کار migration ندارد.
3. image‌های api و worker را دوباره بساز و بالا بیاور. `make verify-live`.
4. **سنجش:** کارت‌های `server_destructive` بازِ همین دستور «خواندن» را (اگر هنوز منتظرند) در گزارش نام ببر. مالک میتواند رد یا مُهرشان کند.
5. گزارش کوتاه فارسی به مالک.
