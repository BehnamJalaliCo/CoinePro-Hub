## ۱. backup ساعتی و پیوسته (§۱۸.۹)
**هدف:** از دست دادن حداکثر **یک ساعت** داده در بدترین حالت بیرونی، و **چند دقیقه** روی خود سرور؛ همه‌چیز رمزنگاری‌شده؛ بازیابی آزموده.
1. **WAL پیوسته:** `archive_mode=on` در Postgres و **WAL-G** (Apache-2.0، نسخه‌ی pin) به پوشه‌ی محلی `/home/Hub/backups/wal/` (دسترسی `700`).
   base backup روزانه با WAL-G. **PITR** تا هر دقیقه روی همین سرور. `archive_timeout=60s` تا عقب‌ماندگی WAL از یک دقیقه بیشتر نشود.
2. **restic** (BSD-2، نسخه‌ی pin) با backend ‏**rclone** به **Google Drive** مالک:
   - مخزن: `rclone:gdrive:CoinePro-HQ/restic`. رمز مخزن restic در OpenBao (`kv/backup/restic`)؛ **مالک یک نسخه‌ی کاغذی هم نگه میدارد** (در گزارش بگو که باید این کار را بکند؛ مقدار را چاپ نکن).
   - **هر ساعت** (systemd timer `coinepro-hq-backup-hourly.timer`، با تأخیر تصادفی تا ۳ دقیقه): dumpهای فعلی (`pg_dump -Fc` هر دیتابیس، `globals.sql`)،
     پوشه‌ی WAL و base backupها، `hq-files` (فایل‌های مالک)، لنگرهای Audit، و snapshot رمزنگاری‌شده‌ی OpenBao (`bao operator raft snapshot save` با یک توکن
     **فقط snapshot** که مالک میسازد؛ تا آن موقع این قسمت خاموش و در گزارش «منتظر مالک»).
   - نگهداری: `--keep-hourly 168 --keep-daily 90 --keep-weekly 52 --keep-monthly 36 --keep-yearly 10` (فضا کافی است). `restic check` روزانه با `--read-data-subset 5%`.
   - backup شبانه‌ی فعلی میماند (محلی، ۷ روز).
3. **اتصال Google Drive (کار خود مالک، در ترمینال SSH خودش):** `make gdrive-auth`:
   - توضیح فارسی کوتاه چاپ میکند؛ مالک روی کامپیوتر خودش `rclone authorize "drive"` را اجرا میکند (با scope ‏`drive.file`، یعنی rclone فقط
     فایل‌های خودش را میبیند)، و JSON توکن را در prompt **بدون نمایش** میچسباند؛ اسکریپت آن را مستقیم در OpenBao (`kv/backup/gdrive`) میگذارد.
   - پیشنهاد در RUNBOOK: یک **OAuth client ID اختصاصی** در Google Cloud مالک (سهمیه‌ی جدا از client عمومی rclone). اختیاری.
   - Claude سرور هیچ‌وقت توکن را نمیبیند و چاپ نمیکند. تا وقتی مالک این کار را نکرده، backup ساعتی فقط محلی است و `/backups/status` آن را «پیکربندی نشده» نشان میدهد.
4. **مقصد دوم (اختیاری، خاموش):** `offsite.sh` فعلی (Hetzner Object Storage) به restic دوم تبدیل شود، با همان رمزنگاری؛ با env روشن میشود.
5. **تست بازیابی خودکار هفتگی** (یکشنبه ۰۶:۰۰ تهران): آخرین snapshot از Google Drive در محیط موقت بازیابی، همه‌ی بررسی‌های `restore-test` فعلی، به‌علاوه‌ی
   **PITR** به یک لحظه‌ی تصادفی ۲۴ ساعت گذشته. نتیجه در `backup.restore_tests`.
6. **API:** `GET /api/v1/backups/status` و `/backups/snapshots` (مالک، ناظر کل، platform SRE)، طبق §۱۸.۹. **هیچ restore از API ممکن نیست.**
7. **هشدار:** آخرین backup ساعتی موفق قدیمی‌تر از ۲ ساعت ← اعلان فوری (`category: data_loss`) و یافته‌ی ناظر (پروتکل `PR-070`). شکست تست بازیابی ← فوری.
   رویدادهای `backup.done` و `backup.failed` (topic ‏`backups`).
- **تست قبولی:** backup ساعتی روی مقصد ساختگی (rclone `local` در CI) ساخته و رمزنگاری‌شده است (بدون رمز، باز نمیشود)؛ PITR به لحظه‌ی مشخص داده‌ی درست را برمیگرداند؛
  `restic check` پاس؛ قطع شدن مقصد هشدار میسازد؛ هیچ توکن یا رمزی در لاگ، env کانتینرها یا خروجی دیده نمیشود (اسکن خودکار).

## ۲. اینترنت کامل برای ایجنت‌ها (§۱۸.۷، `agents/tools.md` v2)
**اصل:** ایجنت‌ها همچنان shell و شبکه‌ی مستقیم ندارند. اینترنت **از ابزار** میرسد و ابزار در سرویس جدای **`egress`** اجرا میشود.
1. **سرویس‌ها** (ایمیج رسمی و pin؛ کاربر غیر root؛ rootfs فقط‌خواندنی جز tmpfs؛ `cap_drop: ALL`):
   - `egress` (Python، FastAPI): API داخلی برای Tool Gateway؛ تنها سرویسی که به اینترنت میرسد، روی شبکه‌ی جدای `hq-egress`.
   - `searxng` (AGPL-3.0، فقط داخلی): موتور جستجوی خودمیزبان؛ موتورهای عمومی معتبر؛ بدون لاگ query بیرون از ما.
   - `browser`: Chromium با **Playwright** (Apache-2.0) در کانتینر جدا؛ **حداکثر ۲ نشست همزمان**، هر نشست profile تازه و پاک‌شونده، سقف زمان و حافظه.
2. **ابزارها در Tool Gateway** (کلاس‌ها طبق tools.md): `web.search`، `web.read` (HTML به متن خوانا، PDF به متن)، `web.browse` (گام‌های navigate، click، type،
   select، scroll، wait، read، screenshot، download؛ اسکرین‌شات و دانلود به فایل‌های §۱۷.۱ تبدیل میشوند)، `http.request`، `egress.recent`.
3. **محافظ SSRF و شبکه (اجباری، با تست):**
   - DNS را خود `egress` حل میکند و **IP نهایی** را چک میکند، و بعد از هر redirect دوباره.
   - مسدود: loopback، link-local، **RFC 1918 (از جمله `10.10.1.0/24` و همسایه‌های production)**، CGNAT، IPv6 خصوصی و ULA، metadata
     (`169.254.169.254`)، نام‌های داخلی Docker، `hq.coinepro.com/internal`. پورت‌های غیر 80/443 فقط برای API‌هایی که حساب سرویس صراحتاً اجازه میدهد.
   - شبکه‌ی `hq-egress` به هیچ سرویس داخلی جز Gateway راه ندارد؛ با تست اثبات کن.
4. **مرز A3 روی وب (تصمیم مالک):** پژوهش، خواندن و کار داخل ابزارها A0 تا A2 و خودکار است. **تعهد بیرونی** (پرداخت، خرید، انتشار، پیام به آدم بیرونی،
   ساخت حساب، تغییر امنیت حساب) با `needs_owner` رد میشود و ایجنت `propose` میکند.
   - تشخیص: الگوهای فرم پرداخت و checkout، دکمه‌های submit در صفحه‌های ثبت‌نام و پرداخت، و **سیاست هر حساب سرویس** (روش‌ها و مسیرهای مجاز).
   - شک ← رد با `needs_owner` (امن‌ترین).
5. **حساب‌های سرویس:** `GET/POST /tools/accounts` (فقط متادیتا). رمز را مالک با `make account-secret KEY=…` در ترمینال خودش میگذارد (ورودی بی‌نمایش ← OpenBao).
   `egress` رمز را **در لحظه‌ی خروج** تزریق میکند (هدر، کوکی ورود، فرم ورود)؛ مدل هرگز نمیبیندش؛ در لاگ و اسکرین‌شات ماسک میشود.
6. **محافظ داده‌ی داخلی:** پیش از هر query یا URL، اسکنر الگوهای حساس (کد کارمند، ref داخلی، ایمیل و تلفن مشتری، توکن) روی آن اجرا میشود؛ برخورد ← رد و ثبت.
7. **محتوای وب = داده‌ی نامطمئن:** خروجی هر ابزار با برچسب `source: web`، URL نهایی و زمان؛ متن‌های دستوری مشکوک علامت میخورند (`suspected_injection`)
   تا ایجنت و ناظر ببینند.
8. **ثبت:** هر درخواست یک ردیف `egress.log` (§۱۸.۷ `EgressEntry`) + Audit با کلاس. `GET /egress` و `/egress/summary` برای مالک و ناظر.
   سقف‌ها: برای هر اجرا (تعداد درخواست، حجم، زمان مرورگر) و برای هر شرکت در روز. عبور از سقف ← رد با کد `egress_limit`.
9. **SearXNG و مرورگر در پروفایل `lean`** هم روشن‌اند؛ سقف حافظه‌ی واقع‌بینانه بگذار و در گزارش بگو.
- **تست قبولی:** جستجو و خواندن یک صفحه‌ی عمومی کار میکند؛ هر آدرس خصوصی (از جمله `10.10.1.1`، `169.254.169.254`، و redirect به آن‌ها) رد میشود؛
  فرم پرداخت در یک صفحه‌ی آزمایشی رد میشود با `needs_owner`؛ رمز حساب سرویس در هیچ پاسخ، لاگ یا اسکرین‌شاتی نیست؛ query با داده‌ی داخلی رد میشود؛
  سقف‌ها کار میکنند؛ کانتینر `egress` به Postgres، Valkey، NATS و OpenBao راه ندارد (جز آنچه صراحتاً لازم است، از مسیر Gateway).

## ۳. پل MCP (§۱۸.۷)
1. Tool Gateway **کلاینت MCP** میشود (کتابخانه‌ی رسمی MCP برای Python، MIT). هر سرور MCP یک ردیف `tools.mcp_servers` است: transport (`http` بیرونی از مسیر
   `egress`، یا `container` برای سرورهای stdio در کانتینر جدا و بی‌شبکه جز `egress`)، ابزارها با **کلاس** هر کدام، شرکت‌های مجاز، و رمز در OpenBao.
2. **فعال شدن فقط با مُهر مالک:** `POST /tools/mcp` (افزودن، 🔏 هش بدنه) و `/tools/mcp/{key}/enable` (🔏). ابزار ناشناخته‌ی یک سرور همیشه رد میشود؛
   تغییر فهرست ابزارهای یک سرور بعد از به‌روزرسانی آن، تا مُهر دوباره خاموش است.
3. `mcp.call` در Gateway: allow-list نقش، کلاس ابزار، سقف، Audit، و خروجی با برچسب داده‌ی نامطمئن.
4. **پیشنهاد اولین سرورها** (هیچ‌کدام بدون مُهر روشن نمیشود): GitHub (فقط خواندن)، Google Search Console، Google Analytics، و fetch/time. در گزارش فهرست کن.
5. `GET /tools/catalog`: همه‌ی ابزارها (داخلی، وب، MCP) با کلاس، نقش‌ها و وضعیت.
- **تست قبولی:** یک سرور MCP آزمایشی (fake) فقط بعد از مُهر کار میکند؛ ابزار A3 آن به تصمیم تبدیل میشود؛ ابزار تازه‌ی سرور بدون مُهر رد میشود؛ رمز سرور در خروجی نیست.
