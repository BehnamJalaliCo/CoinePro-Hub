# کارگاه با دست: Claude Code روی سرور هاب برای هر کاری

> طرح، ۲۰۲۶-۱۱-۰۹. Claude سشن مشورت. تصمیم مالک در همین گفتگو.
> **وضع:** کد نوشته شد (قرارداد §۴۳، پرامپت ۳۰). بررسی Claude سرور: `docs/ops/reports/WORKSHOP_REVIEW.md`. بخش «آنچه ساخته شد» پایین این سند است.

## مسئله
مالک میخواهد شرکت برای **هر کاری** دستش باز باشد: ریلز امروز، ویدیوی یوتیوب فردا، پست X، رصد سئو، و هر چیز دیگر.
- برای هیچ‌کدام نباید Claude سشن مشورت مسیر تازه بسازد.

امروز ایجنت‌های اپ «مغز بی‌دست» هستند:
- هر بار فقط میگویند کدام دکمه (ابزار) زده شود، از فهرستی ثابت.
- کاری که دکمه ندارد، مثل ساخت ویدیو، به بن‌بست میخورد یا فقط «بسته‌ی متنی» میشود.

ولی هاب یک سرور است و Claude Code با دست روی آن هست، یعنی همان Claude سرور هاب. فقط این دو به هم وصل نبودند.

## تصمیم مالک
- **اپ فقط وسیله‌ی ارتباط است.** سرور کامپیوتر است، و Claude Code روی سرور مغز و دست دارد.
- هر کاری که ایجنت دکمه‌اش را ندارد، به **Claude Code روی سرور هاب** داده میشود:
  - Opus 5.5
  - توکن نامحدود
  - تا ۶۰ دقیقه برای هر کار
- **تحویل:** خروجی‌اش، مثلاً ویدیو، با لینک در جلسه به مالک میرسد. اگر مالک تأیید کرد، کار تا انتشار ادامه پیدا میکند.

## طرح: سه تکه، یک بار برای همیشه

### ۱. کامپیوتر: کاربر قفل‌شده روی سرور هاب
- **کاربر:** یک کاربر لینوکس جدا (پیشنهاد: `studio`) روی همان سرور هاب. هزینه‌ی تازه ندارد.
- **آنچه ندارد:**
  - دسترسی به `/home/Hub` و `.secrets`
  - گروه `docker`
  - sudo
  - دسترسی به OpenBao و Postgres (فقط از راه API هاب، مثل هر runner)
- **runner:** `hq-runner` (0.3.1 به بعد) زیر همین کاربر، جفت‌شده به‌عنوان سرور «کارگاه» **شرکت هلدینگ**.
- **ابزارها:** یک بار زیر همان کاربر نصب میشوند، در خانه‌ی خودش: `ffmpeg`، `chromium` (Playwright)، `node`، `python` و فونت IRANYekanX.
  - از آن به بعد Claude Code هر چه لازم داشت را خودش در پوشه‌ی کار میسازد.
- **قدم مالک (قانون ۴، کاربرها با مالک است):** ساختن کاربر با یک دستور که Claude سرور میدهد، یا اجازه به Claude سرور که بسازد.

### ۲. سیم: هر نقش، هر شرکت، هر کار
- **ابزار:** همان `server.claude` (قرارداد §۲۶.۲) روی سرور کارگاه هلدینگ، برای **همه‌ی نقش‌های همه‌ی شرکت‌ها**.
  - مرز داده‌ی شرکت‌ها سر جایش است: کار هر شرکت در پوشه‌ی کار خودش (`~/hq-workspace/W-…`) است، و Audit آن را ثبت میکند.
- **مدل و سقف:**
  - `model: claude-opus-5-5`، `effort: high`
  - بی `token_cap` (توکن نامحدود)
  - `timeout_s: 3600`
  - **پایان ۶۰ دقیقه:** کار میایستد و یک قدم در جلسه دلیلش را میگوید؛ هیچ‌وقت بی‌صدا گیر نمیکند.
- **اکانت:** همان اکانتی که هاب رویش است (پرامپت ۲۹ و ۲۹.۱)، با سوییچ خودکار.
- **قانون نقش‌ها** (منشورها و `agents/tools.md`):
  - هر کاری که دکمه ندارد، **به کارگاه میرود.**
  - هیچ نقشی دیگر نمیگوید «ابزار نداریم».
  - بریف کارگاه = خواسته‌ی مالک، به‌علاوه‌ی «هر فایل تحویلی را در `out/` بگذار».

### ۳. برگشت: فایل‌ها در جلسه
- **runner:**
  - بعد از هر کار `claude` که پوشه‌ی کار دارد، فایل‌های `out/` را به هاب میفرستد.
  - **مسیر:** یک route تازه برای runner با سقف اندازه (پیشنهاد ۲۰۰MB برای هر فایل).
  - **نوع‌های مجاز:** ویدیو، تصویر، PDF، متن و ZIP.
- **هاب:**
  - هر فایل را فایلِ **همان فرمان** میکند (§۳۶.۳) و یک خروجی جلسه میسازد.
  - در اپ «باز کن» و «دانلود» دارد.
  - مسئول جلسه لینک را میگوید و منتظر «تأیید / اصلاح» مالک میماند.
- **بعد از تأیید:** انتشار از همان راه همیشگی ادامه پیدا میکند (IG-Hub برای اینستاگرام).

## چه چیزی عوض نمیشود
- **مغز ایجنت‌ها:** همان مسیر router و خزانه‌ی توکن است. کارگاه فقط برای کارهایی است که «دست» میخواهند.
- **کار ویرانگر:** hook کارهای ویرانگر runner سر جایش است. مُهر مالک برای کار ویرانگر همان است.
- **سرورهای شرکت‌ها:** کار کد خود هر شرکت همچنان روی سرور خود آن شرکت است (`server.claude` با `cwd` ریپو).

## آزمون اول
موشن‌گرافی «اندیکاتور ATR» پروچارت، از جلسه‌ی F-0014:
- **ساخت:** Claude Code در کارگاه آن را میسازد: کد انیمیشن و رندر با ffmpeg.
- **تحویل:** فایل MP4 در جلسه میرسد.
- **انتشار:** مالک نگاه میکند و تأیید یا اصلاح میکند. بعد ادامه تا انتشار.

## پرسش‌های باز برای Claude سرور هاب
1. **حافظه:** حافظه‌ی آزاد واقعی هاب برای یک Claude Code و رندر Chromium و ffmpeg چقدر است؟ آیا در کنار سرویس‌ها جا میشود؟
2. **جفت کردن runner:** آیا runner را میشود روی خود هاب زیر کاربر دیگر جفت کرد، به‌عنوان سرور شرکت هلدینگ؟ مانعی در کد pairing یا OPA (اجازه‌ی `server.claude` برای نقش‌های شرکت‌های دیگر روی سرور هلدینگ) هست؟
3. **فایل‌ها:** نزدیک‌ترین راه موجود برای فرستادن فایل از runner به هاب و چسباندن آن به فرمان چیست؟
4. **فایروال:** هر چیزی که نیاز به تغییر SSH یا فایروال دارد را فقط بنویس؛ انجامش با مالک است.

## آنچه ساخته شد (۲۰۲۶-۱۱-۰۹، بعد از بررسی Claude سرور)
**جواب‌های بررسی:**
1. **حافظه:** جا میشود. کمترین حافظه‌ی آزاد در ۷ روز ۸۰۴۸ MB بود و یک کار در اوج ۲ تا ۳ GB میگیرد. سقف systemd برای کارگاه: ۴GB و ۶ هسته از ۸.
2. **جفت کردن:** سه مانع بود و هر سه برداشته شد:
   - pairing هلدینگ را میپذیرد.
   - مسیر جدای کارگاه در api.
   - قاعده‌ی `via: workshop` در OPA.
3. **فایل:** از همان ماشین آپلود مالک (route تازه‌ی runner) استفاده شد، با Caddy جدا (201MB) و runner 0.3.2.
4. **فایروال:** دیوار شبکه‌ی کاربر `studio` پیش از روشن شدن runner لازم است، چون Temporal روی `127.0.0.1` احراز هویت ندارد. اجرایش با مالک است.

**یک ابزار برای همه:** `workshop.run {brief, title?, work?}`:
- هر نقش هر شرکت آن را دارد، جز نقش‌های سیستمی.
- **نوبت:** هر نوبت، نوبت محیط کاری همان کار روی سرور کارگاه است. پوشه ماندگار است، و اصلاح مالک نوبت بعد در همان نشست است.
- **مدل و سقف:** Opus 5.5، بی سقف توکن، و حداکثر ۶۰ دقیقه برای هر نوبت (۵۷ دقیقه کار و ۳ دقیقه فرستادن فایل).

**تحویل:**
- **فایل‌ها:** هر فایلی که در `out/` گذاشته شود، فایل شرکتِ همان کار میشود و پیوست خروجی آن کار، با «باز کن» و «دانلود» در جلسه.
- **کار ریشه (خود فرمان):** باز میماند، و مسئول بلافاصله بیدار میشود تا بپرسد «تأیید یا اصلاح؟». بعد از تأیید، انتشار از راه همیشگی است (IG-Hub برای اینستاگرام).
- **کار فرزند:** با همین خروجی تحویل میشود.
- **شکست** (۶۰ دقیقه یا خطا): مسئول با دلیلش بیدار میشود و هیچ‌وقت بی‌صدا نمیماند.

**هیچ چیز مخصوص یک کار نیست:** ویدیو، یوتیوب، X، سئو، گزارش و هر کار دیگری همین یک مسیر است. منشورها همین را میگویند (`_common.md` نسخه‌ی ۱۱).
