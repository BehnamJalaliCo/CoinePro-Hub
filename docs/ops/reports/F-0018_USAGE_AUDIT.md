# ممیزی مصرف Claude در کارگروه ریلز پروچارت (F-0018)

> **دستور مالک (۲۰۲۶-۱۱-۱۳):** «عمیق بررسی بکن ببین کل کارگروه رو کی و چرا انقدر لیمیت مصرف میکرد و یه راه حلی براش پیدا بکن و لحاظ بکن». پیش‌تر: «نه طوری باشه که مدل چیزی نفهمه و نه طوری باشه که هر بار فراخوانده بشه و میلیون‌ها توکن مصرف بشه».
>
> **شاخه:** `server/usage-fixes` (از `server/p37-1-publish-rules`). deploy نشده است.
>
> **یکای هزینه:** دلارِ معادل API با قیمت‌های خود هاب (`llm.connections.pricing`). برای Opus 5.5 در هر میلیون توکن: ورودی ۴، خروجی ۲۰، خواندن کش ۰٫۲ و نوشتن کش یک‌ساعته ۸ دلار. Claude Code همه‌ی نوشتن‌ها را یک‌ساعته میکند. همین دلار با درصد سقف ۵ ساعته جور درمیآید (بخش ۸).
>
> **ساعت‌ها UTC هستند.** تهران ۳:۳۰ جلوتر است.

## خلاصه
1. **سقف اول:** حساب اصلی (`claude-max`) در **۷۶ دقیقه** پر شد، از ۳٪ در ۰۰:۲۳ تا ۹۹٪ در ۰۱:۳۹. ۸۶٪ آن مال دو نشست مستقیم Opus بود، PC-CEO و IG-CEO، که هم‌زمان کار میکردند و هیچ‌وقت نو نشدند. نشست تا ۸۱۰ هزار توکن بزرگ شد و هر قدم همه‌اش را دوباره خواند.
2. **سقف دوم:** همان حساب از ۰۴:۲۰ تا ۰۶:۲۰ دوباره پر شد. **۵۶٪ آن مال کارگروه نبود.** مال Claude Code خود سرور هاب بود (نشست مشورت/هماهنگ‌کننده که خرابی‌های F-0018 را درست میکرد) روی همان حساب. ۳۵٪ مال نوبت‌های PC-CEO بود.
3. **کل روز:** ۷۱ نوبت مستقیم حدود **۱۳۸ دلار** خرج کرد. سهم‌ها: خواندن کش ۴۳٪، نوشتن کش ۳۰٪ و خروجی ۲۷٪. ۵۹٪ خروجی «فکر» بود (effort=max).
4. **خزانه‌ی هاب ۸ برابر نشان میداد.** هاب برای این ۷۱ نوبت **۱۱۰۸ دلار** ثبت کرده بود. علت: جمعِ کل نشست را برای هر نوبت دوباره ثبت میکرد. عدد «حدود ۱۰۰۰ دلار» در دفتر خرابی‌ها از همین بود.
5. **اصلاح:** چهار اصلاح در این شاخه انجام و تست شد. چهار پیشنهاد دیگر تصمیم مالک یا فایل‌های کار دیگری است. «قاعده‌ی مصرف» اتوماسیون روزانه در بخش ۷ است.

## ۴. یک نوبت چقدر و چرا

**پایه‌ی پیش از هر کاری:**
- نخستین فراخوانی نشست تازه حدود ۳۶ هزار توکن دارد: ۱۴٫۷ هزار پرامپت سیستم و ۱۴ ابزار خود Claude Code، که بین نشست‌ها از کش خوانده میشود، و حدود ۲۱ هزار بریف و محیط، که نوشته میشود. هزینه: ۰٫۱۷ دلار.
- ابزارهای ستاد deferred هستند و با ToolSearch بار میشوند. هر نشست ۲ تا ۵ بار ToolSearch زد و ۵۰ ابزار، حدود ۸۶ هزار نویسه، بار کرد.
- **دور و بر نگاه کردن در هر نشست تازه:** ۸ قدم اول همیشه یکی بود: `NOTES.md` (۱۶KB)، تکه‌هایی از `STATE.md` (۶۸KB، که خود نشست ساخته بود)، ToolSearch، `work_get` و `linked_read`. زمینه به حدود ۷۵ هزار میرسد. میانگین هزینه: **۰٫۷۵ دلار**.
- **بریف نوبت‌های بعدی:** هر بار حدود ۱۱ هزار نویسه (حدود ۷ هزار توکن) دوباره فرستاده میشد. این بریف هر ۲۷ قدم برنامه را داشت که ۲۴تایش تمام بود، و یک عنوان خروجی را ۲۰ بار. **برش ۹۰۰۰ نویسه‌ای JSON وسط `outputs` میافتاد،** پس `waiting_on` و `ended_without_answer` هیچ‌وقت به نشست نمیرسید.

  - پیشنهاد: پیش از هر نوبتِ کار flow، اگر خرجِ (اصلاح‌شده‌ی) آن روز از سقف گذشته است، نوبت ندهید و یک خبر بدهید.
  - این دو فایل دست Claude دیگری است؛ فقط شرح داده شد.
- **پ۵. سقف کار فرزند متناسب با کار.**
  - W-000413 (Sonnet medium، ۶ قدم) و W-000415/416 (۸ قدم) هر یک وسط کار به سقف رسیدند و دوباره صادر شدند.
  - برای کاری با قدم‌های معلوم (تراکنش قاعده‌های IG-Hub): یک اجرای `server.claude`، یا سقف قدم بیشتر در منشور (`runner.py:448`).
- **پ۶. اصلاح ردیف‌های گذشته‌ی خزانه (فقط با پشتیبان و تأیید):**

```sql
WITH j AS (SELECT id::text AS job, server_id, created_at, usage->>'session_id' AS sid,
                  (usage->>'cost_usd')::numeric AS total
           FROM infra.server_jobs
           WHERE kind = 'claude' AND usage ? 'session_id'
             AND jsonb_typeof(usage->'cost_usd') = 'number'),
     d AS (SELECT job, total - COALESCE(max(total) OVER (PARTITION BY server_id, sid
                  ORDER BY created_at ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING), 0) AS turn
           FROM j)
UPDATE llm.calls c SET equiv_cost_usd = d.turn
FROM d WHERE c.task_class = 'server_claude' AND c.meta->>'server_job' = d.job AND d.turn >= 0;
```

`llm.usage` و `workshop.sessions.usd` جدا جمع شده‌اند. پیش از اجرا باید دید آیا با این UPDATE دوباره ساخته میشوند.
